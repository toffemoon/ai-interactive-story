# 沉浸式 3D · 去险原型(热/性能 soak)

> 配 `decisions/2026-06-09-沉浸式前端-真3D-可行性.md` 里说的 de-risk spike。
> **一次性测量探针,不是产品代码、不是设计稿。** 目的只有一个:在真·中低端安卓 + 微信内置浏览器上,
> 看持续实时 3D 会不会**热降频 / 掉帧 / 烫手 / 费电**。引擎从来不是问题,热才是——这个就是来量热的。

自包含 3 个文件:`index.html` + `three.module.min.js`(r160 vendored)+ `oc.jpg`(真实 OC 立绘当 billboard)。

## 它渲了什么
程序化 blockout 房间(无灯光 = MeshBasic 模拟"烘焙",运行时零光照成本)+ 书架 **600 本书用 InstancedMesh = 1 个 draw call** + 真实 OC 立绘当**相机朝向 billboard** + 相机**自动缓慢环视**(模拟"在店里走动看",制造持续负载)。已做的移动优化:**pixelRatio 钳到 ≤1.5、限 30fps、无实时光、离屏暂停、实例化**。屏上 HUD 实时显示 fps / draw calls / triangles / soak 计时。

## 怎么测(协议)
1. **托管**(选一):
   - 快速本地(只看功能、**不能看热**):本目录里 `python -m http.server 8000`,手机同 WiFi 开 `http://<电脑IP>:8000/`。
   - **真实测试(推荐)**:把这 3 个文件传到一个 **HK/SG 静态托管**(nginx / 腾讯云 COS+EdgeOne / Vercel 但**用自定义域,别用 \*.vercel.app**——国内会被墙),用**微信内置浏览器**打开。
2. **设备**:真·**1500–2500 元安卓机**(不是旗舰、不是模拟器、不是桌面 Chrome——它们会骗你,测不出热)。也补测一台 iPhone(iOS Safari 是最难的 WebGL 目标)。
3. **动作**:微信里打开页面,**连续看 5–10 分钟别锁屏**(HUD 有 soak 计时),其间留意机身温度。

## 通过 / 不通过门槛(来自 decision)
| 指标 | 通过线 |
|---|---|
| draw calls | < ~100–150(本原型应只十几个) |
| triangles | < ~3 万 |
| fps | **稳定 30**,无热降频导致的帧率崩塌(HUD 大数字:绿 ≥28 / 黄 20–27 / 红 <20) |
| 机身温度 | 不烫手 |
| 掉电 | 可接受 |
| 初载(若托境外) | 跨 GFW 可忍 |

- **过** → 真 3D 去险够了,可以 scope Phase B(混合:小型烘焙 3D 房间 + 2.5D/Live2D 角色,低端自动降级)。
- **不过(尤其 fps 热崩)** → 退回 **2.5D + 预渲染(Option A)**;**别换引擎,引擎不是问题**。

## 它没测什么(别误读)
没测真实房间美术、没测交互/走动操作、立绘是 **billboard(转向相机的纸板,不是真身体在 3D 里转身)**。所以即便过了,"OC 整身转向你"那一个节拍仍要单独用 hero 模型/预渲染转身解决(见 decision)。无头 preview 没 WebGL → 这个**只能真机验**。
