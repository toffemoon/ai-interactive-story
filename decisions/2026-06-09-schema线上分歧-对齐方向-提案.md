# (原提案)schema.sql 与线上库结构分歧 —— 对齐方向

> Yufei(PR #44)和账户系统迁移都撞到这个:`schema.sql` 描述的结构 ≠ 实际线上库,且**两个线上项目之间也不一致**。需主理人定"往哪边对齐"。

## 现状(三处不一致)

| | cards / presets 主键 | id 代理列 | cards/presets 唯一性 |
|---|---|---|---|
| **`schema.sql`(repo 声明)** | `id` 代理主键 | 有 | 账户系统后:部分唯一索引(官方/用户) |
| **PROD(73 局,Render 用,MCP 连的)** | 自然键复合主键 `(kind,name)`/`(name)` | **无** | 原无约束 → 账户系统迁移已 drop PK、补部分唯一索引 |
| **TEST(`yldfnbmpzkzjzjoyvfhb`,4 局,本地 `.env`)** | `id` 代理主键 + `cards_kind_name_key` | 有 | 账户系统迁移已 drop `cards_kind_name_key`、补部分唯一索引 |

- 其它表也有类似分歧:`messages`=`(session_id,seq)`、`memory_vec`=`(session_id,scope,ext_id)` 线上是自然键复合主键,`schema.sql` 写的是 `id` 代理主键。
- **app 代码(`storage.py`)不读任何 `id` 代理列**,全用自然键 → **功能无碍**;但"拿 `schema.sql` 一键建新库"得到的结构 ≠ PROD,埋坑(新环境/迁移/新人 build 出来不一样,PR #44 就是这么撞上的)。

## 待定:对齐哪边

**建议(推荐):以 PROD 现状为准,把 `schema.sql` 改成与 PROD 一致** —— 去掉未使用的 `id` 代理列、用自然键主键、保留账户系统的部分唯一索引;并把 TEST 库也对齐(去 `id`)。
- 理由:`id` 列 app 根本不用;PROD 是实际部署、是真相;改 `schema.sql`(文件)+ 给 TEST 写个对齐迁移,**风险最低、不动 PROD 数据**。

**备选:反过来给 PROD/TEST 补 `id` 代理主键,对齐 `schema.sql`** —— 不推荐:无 app 收益、要动 PROD 结构、风险大。

## 怎么执行(方向定了之后)

1. 按选定方向更新 `schema.sql`(单一真相)。
2. 写一个对齐迁移把 TEST(4)与 PROD(73)形态统一(主要是 TEST 去 `id` / 或反之)。
3. 迁移注意:**MCP `apply_migration` 打到的是 PROD(73);本地 app 走 `.env` 打到 TEST(4)**,改库前先认清连哪个(见个人记忆 ai-story-two-supabase-projects)。
