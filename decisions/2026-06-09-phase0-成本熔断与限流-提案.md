# 决策草案:Phase 0 —— 成本熔断 + 限流(不含账户)

> ⚠️ 触及 LLM 调用路径 + 新增 schema = **引擎核心**,由主理人 Gengyue 设计。代码草案
> (`src/costguard.py` / `migrations/2026-06-09-phase0-cost-guard.sql` / `src/api.py` 改动)
> **默认关闭、不改现有行为**;待压测达标后才合 main、才翻开关。

## 决定(提案)

在做账户系统**之前**,先用最小改动堵住「任何人都能直接打 `/api/story_turn` 烧 DeepSeek key」:

1. **全局每日 USD 硬熔断**:当天累计花费 ≥ `GLOBAL_DAILY_USD_CAP` 或被 kill → **整个服务停止调 LLM**(返回 503)。这是真正的「止血阀」。
2. **按 IP 限流**:单 IP 在 `RATE_WINDOW_SECONDS` 窗口内回合数 ≤ `RATE_MAX_TURNS_PER_WINDOW`,超了 429。
3. **单来源每日回合上限**(`SUBJECT_DAILY_TURN_CAP`,**宽松**,0=不限,靠全局兜底)。
4. **用量记账**:每回合用 `out.usage`(`src/llm.py` 的 `collect_usage` contextvar 累加,`story.py:1457` 落到 `turn.usage`)换算 USD,写 `usage_daily` + `spend_daily`。

> Phase 0 **不引入账户**,按 **IP** keying(`usage_daily.subject = 'ip:<addr>'`),留好 `user`/`phone` 升级口;
> 已有 token 闸的 operator 端点(`/say`、`/inject?now`、`/oc/start`)**不限**(那是我们自己)。

## 为什么这样做

- **烧 key 是成本问题、不是身份问题**,2-3 天可单独解决,不必等整套账户(否则 auth 上线前 key 一直裸奔)。
- **最小爆炸半径**:不碰身份、不改 `sessions/cards/presets` 现有结构、不动 `storage.py` 归属、不动前端 → 是最容易压测、最容易过 Gengyue gate 的引擎核心改动。
- **可独立交付**:即使账户工作延期,它也单独有价值。
- **奠定模式**:Postgres 计数 + advisory lock + contextvar 对账,后续每阶段复用;也先把压测纪律(锁争用、多实例计数正确性)跑出来。

## 怎么实现(代码草案)

- 新模块 **`src/costguard.py`**:`client_ip(request)` / `preflight(ip)→Reservation` / `record(res, usage)` / `stats()` / `set_tripped(bool)`。
- **门控**:`COST_GUARD_ENABLED`(默认 0)未开 → `preflight` 返回惰性 reservation、`record` no-op,**部署本代码不改变现有行为**;迁移建表 + 翻 `COST_GUARD_ENABLED=1` 才生效。
- **计数全走 Postgres,无 Redis**(SlowAPI 内存计数在多 worker 下会少计,弃用)。
- **热路径 `spend_daily` 单行**:用 `pg_advisory_xact_lock(hashtext('spend_daily:'+day))` 串行化,消除 read-modify-write 竞态(整个 `with pool.connection()` 块是一个事务)。
- **预扣对账**(防并发越顶):`preflight` 先按 `COST_RESERVE_USD` 预扣进 `spend_daily`;`record` 用实际 `out.usage` 换算后写回差值(`actual - reserved`);失败回合 `record(res, {})` → 退回预扣。
- **价格只从 `.env` 读**(DeepSeek 价格多次漂移,红线:不硬编码;代码内默认仅兜底,务必按现价配)。Phase 0 用单一进价(把全部 prompt token 按未命中价、保守偏高)算 USD —— 对熔断器是安全方向;cache 命中拆分留作后续细化(现 `_UsageAccumulator` 未捕获拆分)。
- **fail-open**:`COST_GUARD_ENABLED=1` 下 guard 自身 DB 出错 → 放行 + 记 log(计数 bug 不该让玩家玩不了;全局上限恢复后照样熔断)。**这是要在压测里讨论的取舍点**。
- **接入点**:`/api/story_turn`、`/api/story_turn_stream`、`/api/reroll` 三个烧 LLM 的端点,各加 `request: Request` → `preflight`(在 try 之前,503/429 不被保底回合吞)→ `record`。
- **operator 观测/急停**:`GET /api/operator/usage`(读计数)+ `POST /api/operator/usage/kill`(翻全局 kill 开关),沿用 `_require_operator` token 闸。

## 新增 schema(迁移:`migrations/2026-06-09-phase0-cost-guard.sql`,同步进 `schema.sql`)

```sql
rate_limits(key text pk, count int, window_start timestamptz)        -- 原子 upsert 计数器
usage_daily(subject text, day date, turns int, tokens bigint, usd numeric(12,6), pk(subject, day))
spend_daily(day date pk, usd numeric(12,6), tripped boolean)         -- 全局熔断单行
```

均为**新增表**(不改旧表),迁移无破坏性;`usage_daily.subject` Phase 0 存 `ip:<addr>`,Phase 1 改存 `user:<uuid>`。

## .env 新增(占位见 `.env.example`)

`COST_GUARD_ENABLED=0`(开关)、`GLOBAL_DAILY_USD_CAP`(硬全局上限,**按可接受烧钱上限设**)、
`RATE_WINDOW_SECONDS` / `RATE_MAX_TURNS_PER_WINDOW`(IP 限流)、`SUBJECT_DAILY_TURN_CAP`(宽松,0=不限)、
`COST_RESERVE_USD`(每回合预扣)、`COST_INPUT_USD_PER_MTOK` / `COST_OUTPUT_USD_PER_MTOK`(DeepSeek 现价)。

## 压测门槛(合 main 前必须有数据 ·「不验证不进」)

1. **全局上限是否守得住**:并发 burst 下 `spend_daily` advisory lock 吞吐 + 多实例计数正确性 + 预扣/对账精度(越顶不超过一个安全余量)。
2. **限流准确**:单 IP 超窗即 429,窗口滚动正确。
3. **开关回退**:`COST_GUARD_ENABLED=0` 时行为与现状逐字节一致(端点回归)。
4. **已知争用点**:单条 advisory-locked `spend_daily` 行串行化贵请求 —— 测试量级 OK、增长后是吞吐瓶颈,届时再分片或上 Redis(**measured 才上**)。
5. **连接池**:每请求多了 auth/计数读 → `max_size=10`(`db.py:52`)可能吃紧,压测里看,必要时调 `DB_POOL_MAX`。
