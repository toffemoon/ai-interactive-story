# 提案:统一「建卡即按模板格式、读卡按 type 确定性解析」+ 补事件卡 / 设定卡的 AI 建卡引擎

> 给主理人 Gengyue。读卡侧(parsers)已就绪;建卡 / ingest 路径的路由与 LLM 用法属引擎核心 = Gengyue 决策域。本提案陈述方向 + 缺口,不擅改核心。

## Yufei 的方向(2026-06-06)
**用户建立的卡直接按「我们的格式」(vault 卡片模板)生成;之后每次 LLM / 引擎只按对应 type 的格式确定性「读」就好,省掉 identify 的「分析」步骤。每一种类型的卡都要有 reader。**
收益:省 LLM 分析(成本 + 漂移 + 截断风险)、忠实作者结构、快、可单测。

## 现状
- **读卡侧已就位**:`src/parsers.py` 有 6 个按 type 的确定性解析器——`parse_character / parse_player / parse_worldbook / parse_settingcard / parse_event / parse_storybook` + `parse_card(text)`(按 frontmatter `type` 路由)+ `detect_kind(text)`。零 LLM、零 API、有 `tests/test_parsers.py`(9/9 过)。
  - 本次《如我所书》导入器(`scripts/import_amphoreus.py`)已全程走确定性解析(角色卡 / 演出卡 / 世界书 / 故事书 / 8 城邦设定卡),零 LLM、零 L4 泄漏,验证了这条路可行。
- **identify 侧(LLM 分析)**:`identify / identify_player / identify_worldbook / identify_storybook` + `classify_text / identify_auto` + 对话建卡 `build_card`。

## 缺口(给 Gengyue)
1. **事件卡无 AI 建卡 / identify 路径**:`build_card` 的 `_BUILD_SYSTEMS` 只有 characters/players/worlds/stories;`identify_auto` 的 `_KINDS` 只有 character/world/story/player。**事件卡(隐藏事件卡)有 `parse_event`(确定性读),但没有 build_card / identify(AI 建)。设定卡同样缺**(有 `parse_settingcard`,无 build_card / identify)。→ 补 events、settingcard 两类的 build_card 系统提示 + identify 路径。
2. **ingest 路径未优先走确定性读**:用户上传 / 前端 ingest 目前默认走 `identify_auto`(LLM classify + identify)。按 Yufei 方向,应:**`detect_kind(text)` 命中我们的 type(=已是模板格式)→ 直接 `parse_card`(确定性、零 LLM);否则才回退 `identify`(自由散文 / 半成品)。** identify 留作兜底、不删。
3. **build_card 产出对齐模板格式**:对话建卡的产物应能被 `parse_card` 读回(或直接产出结构化 model + 可导出模板 markdown),使「建卡 → 入库 → 运行时读」全程不经 identify 重解析。

## 收益 / 兼容
- 省掉运行时 / 入库时的 LLM 分析步骤(成本、漂移、8K 截断都规避);忠实作者写的结构;每类可单测。
- 向后兼容:`identify` / `build_card` 的 LLM 路径保留,作自由散文 / 不会写模板的用户的兜底。
- 风险面小:读卡侧已落地验证;改动集中在 ingest 路由(优先确定性)+ build_card 扩两类,属引擎 ingest 层,不动记忆 / 状态机 / 召回等核心求值。
