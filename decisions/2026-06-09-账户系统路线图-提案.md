## 背景:现状的两个洞

引擎当前**没有任何账户 / 鉴权**(见 README「硬上线门槛」):

1. **越权**:`session_id` 由前端 `crypto.randomUUID()` 生成、存 localStorage,后端
   `load_session` 仅按这个不透明字符串查库、**不校验归属**(`src/storage.py:47-66`)。
   任何人猜到/拿到 `session_id` 就能读/写/删/续玩别人这局(`GET/DELETE /api/session/{id}`、
   `tail`、`reroll`),`cards`/`presets` 还是**全局共享**、同名互相覆盖(`schema.sql:36,42`)。
2. **烧 key**:`POST /api/story_turn` / `_stream` / `reroll` **零鉴权、零限流、零成本上限**,
   任何人都能直接打、烧 DeepSeek key。

随着测试用户变多,先把这两个洞按优先级堵上,再逐步长成完整账户系统。

## 关键约束(决定了选型)

- **目标用户在国内大陆**;团队**暂无法人主体(只能个人)**。
- 现托管全在**境外**:后端 Render、前端 Vercel、DB Supabase(新加坡 ap-southeast-1)。
- **Supabase 自带 Auth(`*.supabase.co`)在国内被墙/不稳**,且它唯一卖点 RLS 对我们这种
  走 psycopg3、不走 supabase-js 的数据路径**几乎无用** → **Supabase 只当 Postgres 用,
  auth 自己在 FastAPI 写**(对"纯手机号登录"反而代码更少、少一跳)。
- 个人主体下,**现实主登录 = 腾讯云手机号短信验证码**(个人认证可发国内验证码;阿里云已禁个人自用签名);
  **微信网站登录 / 运营商一键登录 / ICP 备案 / 大模型上线登记**均需法人主体 → 先用 provider 抽象层留口,以后换实现不换架构。

### 2026-06-09 拍板更新(优先级与 v1 登录方式)

主理人当日决定,在上表基础上**调整优先级**:

- **压测/防滥用不是当前重点**:现阶段所有测试用户都是**信任用户**,烧 key 风险低。
  → **Phase 0 成本熔断降级为"已实现但搁置"**(代码在 `phase0-cost-guard` 分支、`COST_GUARD_ENABLED=0`,等以后有不信任用户再开),**不挡账户工作**。
- **第一优先 = 账户 + 数据独立**(Phase 1 提前):让每个人的会话/卡库/预设各归各人。
- **v1 登录凭据 = 用户名/邮箱 + 密码**(不是手机号 OTP):信任用户 + 要快,**避开境内短信中继基建**;
  手机号验证码/微信/一键登录全部后置,走 provider 抽象层以后换实现不换架构。
- **老存档:主理人手动迁移**(给运营者端点 `/api/operator/assign_session` 按用户名指派归属),
  **不做前端 localStorage 认领流程**。
- **卡库/预设:每人私有 + 保留官方公共**(旧全局行 `user_id=NULL` 自动成为只读官方内容)。

> 落地:本次 Phase 1 后端(`src/auth.py` + `storage.py` 归属 + `api.py` 接线 + `migrations/2026-06-09-phase1-accounts.sql`)已草于本分支,**门控 `AUTH_ENABLED=0` 默认不改现有行为**。**前端登录 UI + authedFetch 是紧接的下一块**。

### 设计原则

- **先堵烧 key,后做身份**(原计划;现因"用户可信"而把账户提到最前,熔断搁置)。烧 key 是成本/滥用问题、不是身份问题,2-3 天可单独解决;
  不把熔断捆进几周的大 auth PR(否则 auth 上线前 key 一直裸奔)。
- **游客优先**:服务端从第一天就发身份,登录=同一 `user_id` 原地升级 → **迁移几乎零成本**。
- **每阶段一个 PR、一份决策文档、一份压测数据**,绝不 big-bang(big-bang 正是
  `2026-06-04` 决策要防的「未验证核心进 main」反模式)。
- **登录方式 = 手机号+短信验证码(腾讯云)**;微信/一键登录走 provider 抽象,法人到位后再开。

## 数据模型终态(Phase 1-2 落齐;Phase 0 只用后三张)

- `users(id uuid pk, kind guest|phone, phone unique null, status, is_admin, realname/consent 列先留 NULL, created_at, last_seen_at)`
- `auth_tokens(token_hash pk, user_id, kind, device_fp, expires_at, revoked_at, ...)` — 不透明 DB token,登出/吊销=一条 UPDATE(不引 JWT/JWKS/RLS,沿用现 `OPERATOR_TOKEN` bearer 习惯)
- `phone_otp(phone, code_hash, expires_at, attempts, consumed_at, ...)` — 验证码只存 hash
- `sessions`/`messages`/`memory_vec`: `ADD COLUMN user_id`(`sessions.data` jsonb blob 不动,归属是顶层列)
- `cards`/`presets`: `ADD COLUMN user_id NULL`;旧全局行 `user_id=NULL`=只读官方/公共库;
  用户行走**部分唯一索引** `unique(user_id, kind, name) WHERE user_id IS NOT NULL`,旧 `unique(kind,name)` 保留给官方行(迁移不破)
- **Phase 0 三张表**:`rate_limits` / `usage_daily` / `spend_daily`(见 Phase 0 文档)

## 合规:beta vs 正式,两态分明

「面向境内公众提供」是**二元的、不看体量**,而现境外栈**结构性无法正式合规**(Vercel/Render 海外主机无法 ICP 备案)。

- **邀请制 beta(Phase 0-2.5,现在做)硬底线**(国内测试用户看到输出前必须就位):
  1. **内容审核**:对**用户输入 + 每段 AI 输出**都过机器审核再展示/落库(阿里云内容安全/腾讯天御/网易易盾,<¥0.01/次,远低于一次 DeepSeek 调用)。**这是 #1 风险,别拖**——一条敏感/违规中文输出就是「关停+约谈」的扳机。
  2. **显式「AI生成」标识** + 导出隐式元数据(2025-09-01 起《标识办法》/GB 45438-2025 强制)。
  3. **成本熔断**(Phase 0,顺带也压住未审内容的产出量)。
  4. **最简 PIPL 隐私政策 + 手机号收集同意**(单手机号属一般个人信息,无需单独同意;但要告知/最小化/可删)。
  5. 受众保持**邀请制/限额**;**beta 不收身份证**(否则触发 PIPL 敏感信息+单独同意)。
- **正式国内上线(Phase 3,另立项,父 repo 战略决策)硬门槛**:换境内云 + ICP/公安备案;
  **大模型上线登记**(我们只调已备案的 DeepSeek、不微调=轻量路径,但**主体是本项目**去登记,约 3-4 个月、不能先上线再补、需关键词拦截库+测试账号);手机号 PII 出境(迁境内 DB 或走安全评估/标准合同,2026-01-01 起生效);需**中国法人营业执照**;若面向 <18 还要防沉迷+监护人同意。

> beta 是**刻意接受的灰色权衡**,有记录;但"没人投诉"≠"合规",法律里没有"安全体量"阈值。

## 待主理人拍板的产品岔路(已收集,部分已有倾向)

1. 现阶段 = **邀请制 beta**(已定);正式上线另立项。

## 风险

- 境外 API 主机国内可达性只能部分验证,是**与 auth 选型无关**的上线风险;Phase 1 加可达性探针早测,若「被墙/慢」可能要上境内边缘入口、影响整个路线图。
- 未审 AI 输出是**今天每回合都存在**的 #1 法律风险(熔断只压量不压内容)→ Phase 2.5 审核闸不能滑。
- 境内短信中继是 Phase 2 关键路径的硬外部依赖。
- 正式上线最终需法人 + 换栈,是工程解决不了的战略决策;若正式上线临近,换栈/法务应**领跑**,本 auth 分阶段部分并入其中。
