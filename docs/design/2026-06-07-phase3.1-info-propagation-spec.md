# Phase 3.1 信息传播 · 设计规格(架构 owner 侧)

> **定位**:这是架构 owner 侧的 Phase 3.1 设计规格,在 Yufei 的设计输入 + **实际代码核查**基础上定稿。
> **只是规格/说明,本轮不落代码。** 按架构主权决策(`decisions/2026-06-04-architecture-ownership.md`),引擎核心要压测验证才进 main;本文件供将来实现时照着做。
> 2026-06-07 决定:**采纳 Yufei 思路、按本规格分层实现,先留说明、暂不排期编码。**

---

## 0. 决策摘要

- **采纳** Yufei 的核心思路:3.1 = Phase 3.0 `knowers` 字段的**「写向」**,不是新系统。**经代码核查成立**(见 §1)。
- **分层落地**:3.1-a(确定性,先做)→ 3.1-b(判断密集,门控+压测)→ 可推断(押后)。
- **边界**:一跳显式分享 + 派系公告**封顶**,不做多跳流言级联;知识**粘**(获得后不回滚)。

---

## 1. 现状锚点(代码核查结论 —— 为什么"写向"成立)

Phase 3.0 的 `knowers` 是**真·已上线、可写、读时已过滤**的字段,不是 #16 移除的旧设计:

- **写**:`src/story.py` ~1378–1394 —— 建派生事实那刻,`knowers = sorted(本轮在场实体键 + 玩家)`,写进 `d["knowers"]`,受 `PHASE3_KNOWERS` 门控。
- **读**:`src/story.py` ~194–208 —— `by_knower=True` 时,带 `knowers` 的事实只注入到 `knowers ∩ wanted` 的在场角色块(亲历/知情才看得到);**无 `knowers` 的旧事实回退 subject 轴**(向后兼容)。
- **其它已有挂载点**(Yufei 列的,均核实在用):`character_logs[].knows`(`models.py:221` + `story.py:557–568`)、`facts`(FactBoundary 的 `revealed/hidden`,`models.py:223`)、`present_characters`(`models.py:171`)。

⇒ 3.1 的写主要是**在已有 `knowers` 上加「显式分享→写」「派系公告→批量写」两条写规则**,复用 3.0 的读过滤 + Phase 1 认忘,**不需要新存储层**。

### ⚠️ 两个实现必须注意的约束(Yufei 输入没点透)

1. **`knowers` 是实体键、挂在派生事实(lm scope)上**;而真正修好"悟空案"的逐轮 `present`(角色**名**,`src/memory.py` 的 `[当时在场]` tag + 确定性删除)是**另一条路径**。3.1 的写**只优雅覆盖 knowers/lm 这一条**;近期对话原文 + 全角色共享摘要那两条短路径它管不到(与 3.0 本就存在的短路径缺口一致)。
2. **角色目前没有 `faction` 成员字段** —— `faction` 现仅是知识条目的 `source` 枚举值(`models.py:53`),不是角色分组;`relationships`(`RelationshipState`,`models.py:220`)在。⇒ **3.1-a 的"派系公告"有前置:得先建一个派系成员模型**(character→faction 或 faction→members),否则"广播给一个派系"无成员可写。

---

## 2. 写向规则(3.1 要新增的)

### 3.1-a — 确定性(先做,几乎免费)
- **显式群体分享 / 派系公告** → 把目标集合**批量并进**该事实的 `knowers`(纯集合写,无额外 LLM)。
- **前置**:派系成员模型(见 §1 约束 2)。过渡期可先用 roster/`relationships` 兜底。
- 当面一对一分享 = 3.0 共场已覆盖(在场即写入 knowers),不需 3.1 额外处理。

### 3.1-b — 判断密集(门控,压测后再默认开)
- 检测**场外/私下「A 告诉 C」**这个分享动作 + 把 C 解析成**实体键** → 写该事实 `knowers`。
- **双重依赖 LLM**:① 从叙事里识别"分享"动作;② told-party 实体消解。DeepSeek 在结构化判断上偏弱 → 独立 flag,默认关,压测达标才开。

### 押后 — 可推断
- C 没见证但能推理得知 —— 旧设计也无低成本解,留更后。

---

## 3. 边界(避免"多跳流言=全知")

1. **跳数封顶**:只「一跳显式分享」+「派系公告」,**不做自动多跳级联**。
2. **scope 在扩散那刻**按当时关系图判定;**知识粘**:已获得不回滚(背叛盟友不让他忘掉旧秘密)。
3. **分层纪律**(成本可控前提):只对**反复出现的重要 NPC** 建知识视图、只对**重要秘密**设显式 scope;琐碎事实默认公开、路人不进 knowers。

---

## 4. 风险(实现/排期前须知)

- **全系统 bookkeeping 最重的一块**(每事实带 scope、每次生成过滤,现在再加写向)。
- **3.1-b 全押 tag 准确度**:动作识别或实体消解错 → `knowers` 写错 → 剧透(不该知道的知道)或失忆(该知道的不知道)。
- **实体键一致性**:told-party 必须解析到与写入端一致的实体键(同角色名变体问题)。
- **ROI / 机会成本**:真实数据均 **~17 轮/局**(production 65 局/1090 轮,最长单局 106)。信息传播价值主要在**长局多角色多场景**才显现 → **3.1-b 当前偏早**;3.1-a 即便补了派系模型,优先级也低于 P0(角色卡 hidden/versions)。

---

## 5. 压测验收门槛(进 main 的条件)

沿用 Phase 3.0 的 eval 矩阵,新增传播专项:

- **缺席认忘不退化**:没被传播到的角色仍诚实认忘(回归不破 3.0)。
- **在场/已知不回退**:3.0 共场知情者不受影响。
- **传播正确**:显式分享 / 派系公告后,**被传播者确实知道**;**范围外的人仍不知道**(剧透率=0)。
- **成本与延迟**:3.1-b 的额外 LLM 调用成本可接受。
- **多种子**(3.0 当前单种子,3.1 要加种子)。
- **一键回退开关**:`PHASE3_*` 风格 flag,出问题即关。

---

## 6. 落地顺序(将来实现时)

```
1. 建派系成员模型(3.1-a 前置)
2. 3.1-a 批量写 knowers(确定性)+ 压测(§5)
3. flag 后做 3.1-b 检测+实体消解 + 压测,过了才默认开
4. 可推断 —— 押后
```
