# 沉浸式前端 · 技术总览(工程层)

> 配 `2026-06-09-immersive-frontend-bookshop.md`(愿景)。本文只谈**怎么用技术落地**,不碰视觉/美术设计(那由人定、AI 执行)。
> 一句话结论:**不是选"一个引擎",而是分三层叠加的混合方案;现有零构建扁平 App 永久当外壳,沉浸层按阶段加。**

## 0. 标杆的技术做法(从 AK/终末地官网提取)
- 明日方舟官网 = **Next.js 打包** + 自有 **CDN `web.hycdn.cn`** + 首页 **Canvas 粒子动效**。
- 含义:**这个完成度是"打包框架 + CDN + Canvas/WebGL 动效"堆的,零构建到不了**——印证下面的构建决策。

## 1. 推荐:分阶段混合(不是一个引擎)
渲染其实是**三件不同的活**,各用最便宜的技术:
- **galgame 对话层**(全屏背景 + 立绘 + 对话框 + 选项)= 纯 React + CSS,**复用现有 `StoryPanel` + SSE 流式渲染,零新依赖**(对话框就是现在的回合渲染换皮)。
- **涟漪/溶解转场** = 一个极小的 **GLSL 着色器**(全屏 WebGL 单 quad,几 KB)+ **CSS clip-path/opacity 兜底**(无 WebGL / prefers-reduced-motion)。
- **"推门走进书坊 → 镜头到糖沐"** = **预渲染图序列 scrub 到 `<canvas>`**(Apple AirPods 那种技术,正是愿景里说的 **分镜→AE** 管线)——**不是实时 3D**。
- **立绘**:先 **静态 PNG/webp + CSS 微动**(眨眼/呼吸/说话抖动,覆盖 ~80% galgame 体感);**只把两个主角(糖沐 + 玩家 OC)后期升 Live2D Cubism**(现规模免费),自托管 UMD + pixi-live2d-display、独立 canvas、30fps、离屏暂停。
- **真 3D 自由漫游**(OC 在空间里转身看你)= **Three.js,仅 Phase 3、仅隔离路由**,绝不进现有 in-browser Babel。

## 2. 构建决策:坚决混合
- **`app.jsx` 永久零构建**(它没有 ES module、单全局作用域,在浏览器编译跑得好,没理由动它)。
- **Phase A–B 全部能塞进零构建**:CSS 对话层、GLSL 涟漪、图序列 canvas、静态立绘、甚至 Live2D(UMD 全局 `<script>` 加在 app.jsx 前 + `?v=` 击穿)——**不需要打包器**。
- **只有真 Three.js 自由漫游才需要 Vite**:且只给**一个隔离路由 `/immersive/`**(单独 entry 打包到 dist,第二个 StaticFiles 挂载,排在 `/api` 和现有 `/` 之后;Vercel 第二份构建保留 /api rewrite),硬跳转进入(进店本来就是场景切换),**完全不碰那 3000 行 app.jsx**。

## 3. 国内 + 移动端(#1 工程风险,且已存在)
- **现在就有的隐患**:`index.html` 从 **unpkg 硬加载 React+Babel**(render-blocking、无国内 POP、2025 末有 >30min 宕机记录)——**unpkg 一卡,整个 App 挂不起来**。
- **最高杠杆的修复(独立于沉浸式,该立刻做)**:**自托管 React(用 production 构建、别用 .development.js)+ Babel/预编译 + 以后每个库**到 Render/Vercel 同源,可选前置 **腾讯 EdgeOne 免费(2300+ 国内节点、无需 ICP)**。字体已是系统字体(安全)。
- GPU 工作的**真正瓶颈是低端国产安卓的性能/电量,不是下载**:着色器只用一个全屏 quad、Live2D/动画锁 30fps + 离屏暂停 rAF、按"房间"懒加载。
- **验证坑**:无头 preview **没有 WebGL**(见记忆 preview-webgl-canvas-false-negative)——所有 WebGL 特性必须优雅降级,且只能在真机/真浏览器验,preview 截图会 30s 超时。

## 4. 隐藏的长杆:立绘绑定(rigging)
- niji7/libtv/GPT-Image 出的是**扁平单层图**;Live2D 要**分层**(眼/眉/嘴/发)。**runtime 不是难点,把扁平图拆层 + 在 Cubism Editor 绑定才是**(每个角色一道美术工序;可试 AI 自动分层再人工修)。
- **先拿一个角色把"扁平→分层→绑定→真机能加载"整条跑通**,再铺开。

## 5. 阶段路线(技术里程碑)
- **Phase 0(可靠性,先做、与沉浸式无关)**:自托管 React 生产版 + Babel 去掉 unpkg 依赖;加 webp 资产预处理(响应式 1x/2x + avif 走 `<picture>`);定预算(外壳 ~1–1.5MB,每场景 400–800KB)。**无视觉变化,纯工程加固,是后面一切的前置。**
- **Phase 1(扁平,现栈)**:VN 对话层(复用 StoryPanel + SSE)、静态立绘 + CSS 微动、新沉浸屏作为现有 `view` 开关的新值;糖沐对话式商城/搜索/充值、书架=我的 = 换皮 + content/prompt。零新依赖。
- **Phase 2(局部沉浸,仍零构建)**:GLSL 涟漪转场(+CSS 兜底)+ 预渲染图序列推门动画;可选两主角升 Live2D(UMD 自托管,先验一个角色全链路)。仍无打包器。
- **Phase 3(全沉浸,仅当真要自由漫游 3D)**:Vite 隔离路由 + Three.js 懒加载;真机验证;硬跳转。app.jsx 不动。

## 6. 待主理人定(关键岔路)
1. **"第一人称走进 3D 书坊"有多字面?** —— ① 舞台化电影感(预渲染图序列 + CSS-3D 视差,**零构建、移动安全、~90% 效果/<10% 成本**)/ ② 真自由漫游 3D(实时 Three.js,强制打包器 + 国产安卓性能风险 + preview 无 WebGL 验证缺口)。**这是最大的成本/架构岔路,且是设计方向决定——下游(构建/预算/资产)全看它。**
2. **主角要不要"真活"**(转头/视差/真口型)= 静态 PNG+CSS 够不够,还是上 Live2D(引入 WebGL 运行时 + 绑定工序 + 规模化后的授权费)。
3. **国内分发**:只自托管(去 unpkg)/ 再加 EdgeOne 免费 CDN / 重资产走阿里云 OSS。
4. 何时(若有)合并成单一 Vite SPA vs 永久混合(推荐永久混合,最低风险)。

## 风险摘要
零构建对每个新库/大资产都要每次重编译/重解析(保持沉浸代码精简、只预打包重 3D 块)· unpkg 是当下活的国内可达性隐患(自托管是硬前置)· 纯 DOM/CSS 做不出真 3D 景深(诚实的天花板)· GPU 在低端安卓的性能是 GPU 工作的硬约束 · preview 无 WebGL 的验证缺口 · rigging 是每角色的美术长杆 · 单 useState 路由无 history/深链(沉浸多房间流要补)· Live2D/Spine 的授权随规模成本 · 图序列是烘焙路径、流量重 · /api(DeepSeek)跨境不可缓存,前端优化盖不住。
